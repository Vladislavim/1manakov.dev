## Посмотрите на одну кнопку

Представьте два раздела одного сайта. В первом кнопка «Отправить» блокируется на время запроса и показывает прогресс. Во втором её можно нажать повторно, а подпись остаётся прежней. Цвет и радиус совпадают, но поведение различается. Визуальная библиотека эту проблему сама по себе не решает.

UI kit может содержать все нужные состояния кнопки. Однако команде ещё нужно договориться, в какой момент включать каждое состояние и какой результат ожидается после ответа сервера. Такие правила связывают нарисованный компонент с реальным сценарием.

## Что действительно нужно маленькому сайту

Для компактного проекта не обязательно начинать с отдельного портала документации. Достаточно описать повторяющиеся элементы: типографику, интервалы, ссылки, кнопки, поля и сообщения. Рядом с каждым компонентом сохраните пример применения и одну типичную ошибку. Это полезнее большой библиотеки вариантов, которые пока нигде не используются.

Проверьте, можно ли изменить компонент в одном месте и получить предсказуемый результат на всех страницах. Если каждый экземпляр вручную переопределён, формальное наличие библиотеки почти не помогает. Сначала разберите причины переопределений: часть может быть оправдана контекстом, а часть накопилась случайно.

## Когда правил становится недостаточно

Система требует явного сопровождения, когда над продуктом работают несколько команд, компоненты имеют разные реализации или изменения затрагивают много сценариев. Тогда важно определить владельца, порядок обсуждения и способ сообщить о новой версии. Иначе два одинаково названных компонента постепенно становятся разными.

Не объединяйте элементы только потому, что они похожи. Кнопка подтверждения оплаты и переключатель режима решают разные задачи. Общими могут быть визуальные токены, но семантика, состояние ожидания и обработка ошибки должны сохранять различия.

## Как выбрать следующий шаг

1. Возьмите три реальные страницы и отметьте повторяющиеся элементы.
2. Сравните их состояния в макете и работающем интерфейсе.
3. Выберите одно расхождение, которое мешает пользователю закончить задачу.
4. Исправьте общий компонент и запишите правило, предотвращающее повторение.

Результатом первого прохода должен стать работающий договор о нескольких элементах, а не максимальное число компонентов. Таблица выше служит рамкой для выбора: конкретный UI kit тоже может включать документацию, а небольшая дизайн-система может обходиться без сложной инфраструктуры. Название инструмента не заменяет проверку того, как команда им пользуется.

Правила компонента можно проверить в [прототипе конкретного сценария](/guides/website-prototype-scenario).
