# Загрузка imanakov.dev на обычный хостинг

Архив `imanakov.dev-hosting.zip` содержит готовый сайт. Node.js, npm, база данных и VPS на хостинге не нужны. Домен пока заложен `https://imanakov.dev`.

## Что покупать

Обычный Linux-хостинг с HTTPS, Apache 2.4 (или совместимым LiteSpeed), поддержкой `.htaccess`, `mod_rewrite`, `AllowOverride` для правил из архива. Достаточно одного сайта; объём файлов указан в `manifest.json`. Сертификат нужен для imanakov.dev и www.imanakov.dev. Для зоны .dev HTTPS обязателен.

У провайдера с чистым Nginx вместо `.htaccess` необходимо применить правила из `scripts/hosting/nginx-location.conf` через поддержку или панель. Простая загрузка файлов без правил не гарантирует работу адресов без расширений и редиректов. До оплаты уточните поддержку этих правил.

## Порядок загрузки

1. Создайте сайт для домена, направьте DNS на хостинг, включите сертификат и его автопродление.
2. Если сайт уже существует, сохраните резервную копию его файлов и настроек.
3. Распакуйте **содержимое архива** в корень сайта (`public_html`, `www/imanakov.dev` или путь из панели). `index.html`, `.htaccess`, `_next`, `images`, `fonts` должны лежать непосредственно в этом корне. Не загружайте исходники, `.env`, `node_modules` и папку проекта.
4. Включите отображение скрытых файлов и убедитесь, что оба `.htaccess` загружены. Права каталогов 755, файлов 644.
5. Откройте главную, `/about`, `/work/allnrg`, `/guides`, статью и `/lab` напрямую и после обновления страницы. Проверьте навигацию, изображения, попап и мобильную версию.
6. Проверьте: HTTP → HTTPS, www → без www, `/play` → `/lab`, `/journal` → `/guides`; несуществующий адрес должен отдавать **HTTP 404**, а не главную с кодом 200.
7. Проверьте `/robots.txt`, `/sitemap.xml`, `/sitemaps/site`, `/sitemaps/guides-0`, `/feed.xml`. XML должен открываться с типом `application/xml` (RSS допустим `application/rss+xml`). После запуска подтвердите домен в поисковых кабинетах.

Правила HTTPS учитывают `X-Forwarded-Proto`. Если хостер использует другую схему проксирования, настройте HTTPS-редирект в его панели и отключите соответствующий блок `.htaccess`, чтобы не получить цикл. На временном техническом домене сначала согласуйте редирект: архив перенаправляет HTTP на основной домен. Предпросмотр публичного технического домена нужно закрыть от индексации средствами хостинга.

## Повторная сборка и обновление

На компьютере разработчика с установленными зависимостями:

```text
npm ci
npm run build:hosting
npm run check:hosting
npm run package:hosting
```

`package:hosting` использует Python 3 (стандартная библиотека, дополнительные пакеты не нужны). ZIP и контрольная сумма находятся в `outputs/hosting`. Команда `npm run preview:hosting` открывает локальный статический сервер по адресу http://127.0.0.1:3010. Это проверка файлов и маршрутов, не эмуляция Apache/TLS.

Обновляйте сначала `_next` и медиа, затем HTML и текстовые RSC-файлы, сохраняя старые хешированные JS/CSS до завершения загрузки. Предпочтителен атомарный перенос каталога через панель/SSH. Случайное удаление всех старых файлов в начале обновления вызовет простой.

Автоматическая загрузка из GitHub пока **не настроена**: нужны выбранный провайдер, протокол, путь сайта и секреты доступа. Сборка уже вынесена в команды; после выбора хостинга можно подключить деплой без изменения страниц. Секреты хранятся в GitHub Secrets, не в репозитории.

## Ограничения и сохранённое поведение

HTML страниц и SEO-метаданные создаются при сборке; изменения контента требуют новой публикации. Анимации, интерактивные гайды, переходы и попап работают в браузере. Контактные действия по-прежнему открывают Telegram/почту; серверной отправки форм архив не добавляет.

Изображения отдаются готовыми локальными файлами (большинство уже WebP), без серверного `/_next/image`. Серверные редиректы и заголовки перенесены в конфигурацию хостинга. Обычные `npm run build` и `npm start` сохраняют режим Next.js. После статического экспорта для запуска `npm start` сначала снова выполните обычную `npm run build`. Не запускайте две сборки одновременно.

Не меняйте домен только в DNS: при выборе другого имени обновите `NEXT_PUBLIC_SITE_URL`, правила HTTPS/www в конфигурации хостинга и пересоберите архив, затем проверьте canonical и sitemap.
